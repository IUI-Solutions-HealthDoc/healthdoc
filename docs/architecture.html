1. System context

Three worlds talk to each other: the facility edge (a server inside each hospital running the full stack, so the hospital keeps working when the internet doesn't), the cloud (staging/production, the aggregation point facilities sync to), and ABDM (the national health network HealthDoc registers with as HIP + HIU).

Design principle: the facility never depends on the cloud to treat a patient. Registration, queueing, consultations, lab, pharmacy, and billing all run locally; sync is asynchronous. That's why every primary key is a UUID and every row carries updated_at + a sensitivity tier.

3. Request lifecycle — every API call goes through this

The same pipeline applies to all 26 modules. No module skips a stage; the audit write is in the same DB transaction as the mutation, so you cannot change data without a trace.

1 · Clientlib/api.ts adds Bearer JWT, JSON
2 · NginxTLS 1.3 · security headers · rate limit
3 · Envelope middlewareassigns X-Request-ID
4 · Auth depJWT verified vs Keycloak JWKS → CurrentUser
5 · Role gaterequire_roles(…) → 403 if wrong role
6 · Consent gateclinical reads only — consent/ check, denials logged
7 · Service layermodule business logic; cross-module via service calls
8 · One transactionmutation + audit_logs row commit together or roll back together
9 · Envelope out{success,data,error,meta}
Reliability contracts (§4A): every creating POST needs an Idempotency-Key (a retry on a flaky rural link must never create a second patient or a second payment); every mutable clinical/financial row carries row_version and PATCH requires If-Match (no silent lost updates between two clinicians); clinical notes reach Mongo via the outbox, never a direct dual-write; uploads are validated by sniffed magic bytes and served attachment + nosniff.
Failure rule: if the audit insert fails, the business write rolls back too (B7-W1-04). If consent fails, return 403 and write the denial to data_access_log.

Per-facility module toggles — exactly four: pharmacy, lab (pathology), radiology, OT, blood bank can each be switched off per hospital (facility_modules, admin-only, audited). Disabled ⇒ no worklist, no billing accrual, endpoints answer 409 module_disabled, and the frontend hides the surface via GET /facility/capabilities — but clinical records still complete: orders flip to external_referral, prescriptions still print. Everything else is core and can never be disabled — including inventory (consumables/reagents exist without a dispensary), IPD, emergency, ABDM and refunds. Procedures are recorded via procedure_records (owned by orders, not OT) so a minor procedure is captured and billable at a facility with no theatre. Any combination of the four, including all four off, must yield a working hospital: ordering never disappears (orders become external_referral), outside reports come back via order_external_results, billing bills only the lines that exist, and infra follows the toggle — orthanc and icd11 run behind Compose profiles, so a facility without radiology never runs a PACS. Disabling never deletes data; re-enabling never rewrites history.
Boundary rule: importing another module's models is allowed only for FK typing; querying another module's tables directly in SQL is a PR-rejection offense. Cross-module data goes through that module's service functions, so schema changes stay local to their owner.

8. Security architecture (DPDP / ABDM / CERT-In)

Identity & access

Keycloak realm healthdoc; 13 roles (superadmin, receptionist, doctor, nurse, lab_tech, radiology_tech, pharmacist, emergency, hod, supervisor, admin, auditor, patient). Four authority roles are separated by design: superadmin = platform (never patient data, incl. no merge/unmerge) · admin = facility config (appoints HODs) · hod = runs ONE department, scoped by users.department_id · supervisor = records authority (merge/unmerge, different-approver rule). MFA required for admin, hod, supervisor. Superadmin is cloud-only — it owns facilities and appoints admins/DPOs but can never read clinical data. Staff accounts are created via a maker-checker flow (user_account_requests): requester ≠ approver, approval atomically creates the Keycloak account + profile row. OIDC + PKCE, 15-min access tokens, silent refresh. Backend: JWKS-verified JWT → require_roles per endpoint; JWT sub ↔ users.keycloak_sub. No password columns anywhere.

Data protection

Aadhaar: AES-256-GCM ciphertext + HMAC blind index, two separate keys — plaintext exists nowhere (DB, logs, API). Files: private MinIO buckets, presigned URLs, per-access logging. TLS 1.3 only at the edge; HSTS, CSP, frame-deny. Mobile is contact info, never identity.

DPDP Rules 2025 operations

Compliance wave (migrations 0021–0026): DPO registry per facility, patient grievance workflow with 90-day due dates and DPB escalation, breach-notification log tracking both clocks (CERT-In 6 h, DPDP detailed report 72 h), consent-manager registry linked to consent records, guardian verification for minors, and a Postgres audit row for every ABDM FHIR transmission.

Accountability

Append-only, hash-chained, signed audit log written in the same transaction as every mutation; integrity re-verification job; monthly partitions archived to MinIO with hashes. Clinical reads logged to data_access_log including denials and break-glass. Financial rows immutable once issued.
